# Domain glossary

This file records the stored-context vocabulary: space, bundle, item-type, item, doc, file, service, driver, run, hook, capability, and related terms. A bundle owns named *services*, each backed by a *driver* (built-in `http` — what a hook always was — and `mail`, or one the operator installs); calling a service starts a durable, pollable *run*. "Hook" persists only as the legacy alias surface kept until 1.0 (`fire_hook`, the `/v1/**/hooks*` REST routes, `YAP_HOOK_*` env vars).

- **Instance** — a Yap installation rooted in a directory: its `.env` (operator configuration and keys), `data/` (database and blobs), vendored server (`node_modules/yap-core`), and CLI state (`.yap/`: pidfile, logs, saved credential). The `yap` CLI operates on whichever instance directory it runs from. Instance layout and behaviour — paths, env resolution, running state, vendored-server lookup, delegation — are owned by the `src/instance/` module, which ships in both `yap-core` and the manager-only `yap-cli` and depends only on Node builtins.
- **Vendored server** — the instance's own copy of `yap-core`, installed into the instance directory at `yap init` and replaced only by `yap upgrade`, so instances on one machine are isolated from each other and from the global CLI's version.
- **Delegation** — running a server-side command (`serve`, `backup`, `restore`) by spawning the instance's vendored server entry instead of the CLI's own code. Delegation has exactly three outcomes: *ran* (with the child's exit code), *self* (the vendored entry is the running process — caller runs in-process), *absent* (no server installed). What to do about *self* and *absent* — in-process fallback, error, message — is the command layer's policy, never the instance module's.
- **Credential** — a presented bearer secret, resolving to exactly one of three lanes: a user **access key** (identity, full authority), an OAuth **access token** (delegated identity, scope-clamped), or the environment-level **sysadmin key** (operator credential, never a content principal). Resolution is one decision made once, in `src/core/credential.ts`; the transports own only credential *extraction* (REST reads the Authorization header; MCP adds the `?key=` fallback), the *wording* of each rejection, and the *timing* of the token scope context (REST per request, MCP per session).
- **Mail driver** — the second built-in driver (`src/core/drivers/mail/`): one operator-configured IMAP/SMTP account behind seven actions (`folders`, `search`, `read`, `mark`, `send`, `draft`, `delete_draft`). The service's action allowlist and pins are what shape it into a *reader*, a *triage* service (drafts replies into the account's Drafts folder for a human to send — the draft-for-approval workflow), or a *notifier* (`send` with `to` pinned; `to`, `cc`, and `bcc` are treated as one recipient set — pinning any of them locks the others, which the driver learns via `ctx.pinned`). Agent-visible failures are thrown as `YapError`s at the run boundary; everything else collapses to "run failed". Reference: `docs/mail-driver.md`.
- **Driver bundle I/O** — explicit surfaces injected into `RunContext` for operator-installed drivers. `reads: { files: true }` gives `ctx.reader.readFile(refOrId)`, scoped to finalized files in the run bundle and backed by the blob store without exposing storage keys or signed URLs; `stream()` is primary, while `bytes()` and `text()` are capped helpers. `reads: { items: true }` gives `ctx.reader.getItems(ids)`, scoped to the run bundle and materialized by the normal item layer. `writes: { items: true }` gives `ctx.writer.createItems(itemTypeName, values)` and `ctx.writer.updateItems(updates)`, scoped to the run bundle and validated by the item layer. `updateItems` takes the REST/MCP update shape: `{id, set?, edits?}`. `writes: { files: true }` gives `ctx.writer.writeFile({name, mimeType?, bytes})`, scoped to the run bundle and returning a `file://` ref. Undeclared surfaces are `null` unless another read/write surface created the handle, and successful file/item reads plus item/file writes are recorded as metadata on the run row.
- **Action allowlist** — a service's optional `actions` list: which of its driver's actions the service exposes (`null` = all, which is what every service authored before the column existed means). The allowlist is enforced in one place, `allowedActions` in `src/core/services.ts` (stored list ∩ what the driver declares, in the driver's order), and both the agent-visible listing and the runner's action resolution go through it — a disabled action is not listed and is "unknown" to `run_service`, never "forbidden". It narrows *actions*; **pins** narrow *parameters* and stay validated against the driver's full action set, so a pin on a disabled action's parameter is legal and inert.
