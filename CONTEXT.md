# Domain glossary

This file records the stored-context vocabulary: space, bundle, item-type, item, doc, file, service, driver, run, hook, capability, and related terms. A bundle owns named *services*, each backed by a *driver* (built-in `http` — what a hook always was — and `mail`, or one the operator installs); calling a service starts a durable, pollable *run*, and a *schedule* calls one on a cron. "Hook" persists only as the legacy alias surface kept until 1.0 (`fire_hook`, the `/v1/**/hooks*` REST routes, `YAP_HOOK_*` env vars).

- **Instance** — a Yap installation rooted in a directory: its `.env` (operator configuration and keys), `data/` (database and blobs), vendored server (`node_modules/yap-core`), and CLI state (`.yap/`: pidfile, logs, saved credential). The `yap` CLI operates on whichever instance directory it runs from. Instance layout and behaviour — paths, env resolution, running state, vendored-server lookup, delegation — are owned by the `src/instance/` module, which ships in both `yap-core` and the manager-only `yap-cli` and depends only on Node builtins.
- **Vendored server** — the instance's own copy of `yap-core`, installed into the instance directory at `yap init` and replaced only by `yap upgrade`, so instances on one machine are isolated from each other and from the global CLI's version.
- **Delegation** — running a server-side command (`serve`, `backup`, `restore`) by spawning the instance's vendored server entry instead of the CLI's own code. Delegation has exactly three outcomes: *ran* (with the child's exit code), *self* (the vendored entry is the running process — caller runs in-process), *absent* (no server installed). What to do about *self* and *absent* — in-process fallback, error, message — is the command layer's policy, never the instance module's.
- **Credential** — a presented bearer secret, resolving to exactly one of three lanes: a user **access key** (identity: full authority, or a fixed role mask of it when the key is scoped — see **Key scope**), an OAuth **access token** (delegated identity, scope-clamped), or the environment-level **sysadmin key** (operator credential, never a content principal). Resolution is one decision made once, in `src/core/credential.ts`; the transports own only credential *extraction* (REST reads the Authorization header; MCP adds the `?key=` fallback), the *wording* of each rejection, and the *timing* of the scope context (REST per request, MCP per session). The scope context (`src/core/authScope.ts`) records its `source`, `token` or `key`, because the two differ outside capability resolution: an admin-role token may manage credentials, a scoped key never may.
- **Issuer** — the recorded origin of an access key: `user` (minted or rotated by the user over `/v1/keys`) or `sysadmin` (the initial key from user creation, or one issued over the **sysadmin key lane**, `/v1/users/:id/keys`, where the operator issues, lists and revokes keys for any user). A fact, not a kind of key: an unscoped key carries its user's full authority whoever issued it, every key shows up in the user's own key list, and is theirs to rotate or revoke; rotation always yields a `user` key under the same name and scope. Owned by `src/core/keys.ts`.
- **Key scope** — a fixed role mask on an access key, `{role: "admin" | "member" | "read-only"}`, the same masks as an OAuth token's role: effective rights are the user's grants intersected with the mask, enforced in capability resolution exactly as for a token. `null` (the default, and every key from before migration 0016) is an unscoped key. Set when the key is created (`POST /v1/keys`, `POST /v1/users/:id/keys`) and never changed; rotation keeps it. It limits what, never where: `spaces` / `bundles` are refused, since reach is what grants are for (give a machine its own user to limit where it acts). A scoped key is a narrower stand-in for its user, not the user in person, so at every role, admin included: it holds no `manage_keys` (it cannot create, list, rotate or revoke keys or connected apps, and so cannot widen itself), and `pageLogin` refuses it on the consent screen, the connections page, the secret form and the approve page ("This key is limited. Log in with a full key.") — which is what keeps an agent with a scoped admin key from approving its own service. `create_spaces` follows the role: a scoped admin key may, member and read-only may not; `deniedCapabilities` apply on top. `whoami` reports it as `keyScope` (present only for a scoped key). Owned by `src/core/keys.ts`.
- **Sideload** — storing a file from a URL in one synchronous call (`sideload_file`, `POST /v1/bundles/:id/files/sideload`): the server fetches the bytes itself and writes the file finalized, with no reserved placeholder and nothing left behind on failure. The caller supplies a location and nothing else — a GET, no credentials, no headers — and every request, each redirect hop included, goes through the same guarded egress as driver traffic. Agent-facing only: no widget or upload page offers it. The source URL is never stored. `YAP_SIDELOAD_ENABLED=false` switches it off instance-wide, which also stops the tool being advertised.
- **Account capability** — something a user does with their own account rather than inside a space: `manage_keys` (all self-service credential management — the user's access keys, and listing and disconnecting connected apps — as one switch; connecting a new app through consent is not part of it) and `create_spaces`. Held by every user by default; the operator can deny either per user (`deniedCapabilities`, set over the sysadmin lane on user creation or `PATCH /v1/users/:id`). Distinct from a granted **capability**, which is an allow/deny row on a space or bundle. A denial is read from the user's row on every check, so it binds every credential (keys and tokens at any role) from the next operation on, removes authority without revoking or deleting anything, and never applies to the **sysadmin key lane**. Owned by `src/core/accountCapabilities.ts`.
- **Mail driver** — the second built-in driver (`src/core/drivers/mail/`): one operator-configured IMAP/SMTP account behind eight actions (`folders`, `search`, `read`, `attachment`, `mark`, `send`, `draft`, `delete_draft`). `attachment` is the only one that writes into Yap: it stores one listed attachment as a file in the service's bundle (the driver declares `writes: { files: true }`). The service's action allowlist and pins are what shape it into a *reader*, a *triage* service (drafts replies into the account's Drafts folder for a human to send — the draft-for-approval workflow), or a *notifier* (`send` with `to` pinned; `to`, `cc`, and `bcc` are treated as one recipient set — pinning any of them locks the others, which the driver learns via `ctx.pinned`). Agent-visible failures are thrown as `YapError`s at the run boundary; everything else collapses to "run failed". Reference: `docs/mail-driver.md`.
- **Driver bundle I/O** — explicit surfaces injected into `RunContext` for operator-installed drivers. `reads: { files: true }` gives `ctx.reader.readFile(refOrId)`, scoped to finalized files in the run bundle and backed by the blob store without exposing storage keys or signed URLs; `stream()` is primary, while `bytes()` and `text()` are capped helpers. `reads: { items: true }` gives `ctx.reader.getItems(ids)`, scoped to the run bundle and materialized by the normal item layer. `writes: { items: true }` gives `ctx.writer.createItems(itemTypeName, values)` and `ctx.writer.updateItems(updates)`, scoped to the run bundle and validated by the item layer. `updateItems` takes the REST/MCP update shape: `{id, set?, edits?}`. `writes: { files: true }` gives `ctx.writer.writeFile({name, mimeType?, bytes})`, scoped to the run bundle and returning a `file://` ref. Undeclared surfaces are `null` unless another read/write surface created the handle, and successful file/item reads plus item/file writes are recorded as metadata on the run row.
- **Schedule** — a bundle-owned cron (5-field, IANA timezone, UTC by default) that starts a run of one service action with stored params, as its **owner**, the user who created it. Its own object, not a field on the service: one service can carry several. `run_services` is re-checked for the owner on every fire; losing it disables the schedule with the reason recorded. A tick is skipped (and recorded, not failed) while the schedule's previous run is still `queued` or `running`; missed ticks are not caught up. Created, changed, deleted and read with `run_services` alone, over REST and MCP alike (scheduling is running later); only the owner may change what or when it runs, or re-enable it. The record lives in `src/core/schedules.ts`, the in-process firing in `src/core/scheduler.ts`, which serve.ts starts unless `YAP_SCHEDULER=off` — on in exactly one process per database, documented rather than enforced.
- **Run source** — what started a run, recorded on the row with the user it ran as: `mcp`, `rest`, `hook` (the legacy fire surfaces, `fire_hook` included) or `schedule` (with the schedule's id). Null on runs recorded before the columns existed.
- **Action allowlist** — a service's optional `actions` list: which of its driver's actions the service exposes (`null` = all, which is what every service authored before the column existed means). The allowlist is enforced in one place, `allowedActions` in `src/core/services.ts` (stored list ∩ what the driver declares, in the driver's order), and both the agent-visible listing and the runner's action resolution go through it — a disabled action is not listed and is "unknown" to `run_service`, never "forbidden". It narrows *actions*; **pins** narrow *parameters* and stay validated against the driver's full action set, so a pin on a disabled action's parameter is legal and inert.
- **Settings and secrets** — the two parts a service's config is stored in when its driver publishes a config schema. *Settings* are every field not at one of the schema's secret paths: plain JSON, returned to the service's authors (`edit_services`) as `settings` (over REST in the listing, over MCP by `get_service`), never to other readers and never in `load_bundle`. *Secrets* are the values at secret paths: encrypted and write-only, reported only as `secretsSet`, the list of set paths. A config write replaces the settings and merges the secrets (left out = kept, `null` = removed); a run gets the two merged into one object. A driver without a schema keeps one *sealed* config blob. Services from before the split are split at boot by `backfillServiceConfigs`. Owned by `src/core/serviceConfig.ts`; reference: `docs/service-config.md`.
- **Secret request** — a one-off form for entering some of a service's secrets, so they go from a human straight to the server and never through an agent. An agent authoring over MCP sends settings only (a secret value is refused) and calls `secret_request` for the secret paths it needs; the result carries the paths, labels and whether each is set, an origin URL, and a `secret-input` widget pointer. The form posts to `POST /v1/secret-requests/:id/submit` with its own signed token and the person's login (the same **Page login** as an approval: a provider login's ticket, or an access key, where `pageLogin` refuses the sysadmin key, an OAuth token and a scoped key; the agent sees the token, so the token alone saves nothing); one successful submission per form, expiry after `YAP_SECRET_REQUEST_TTL_SECONDS`, and the requester's `edit_services` is re-checked on submit. A submission sets the listed paths only. Owned by `src/core/secretRequests.ts`; reference: `docs/mcp-service-authoring.md`.
- **Approval** — a person's go-ahead for a service written over MCP, which does not run without it. Stored on the service as `approved_at` / `approved_by`; a service with `approved_at` null *waits*. An MCP create waits; an MCP update that changes params, pins, actions, settings or which secrets are set waits again; a REST write of the config, and every service from before migration 0015, is approved, except a REST write made with a scoped access key, which is held to the MCP rule (a create, a config write, or a change to params, pins or actions waits); a secret entered through a secret request keeps it. `prepareRun` refuses a waiting service, so runs and schedules both stop. An *approval request* (`approval_request`, `POST /v1/services/:id/approval-request`) is a one-off approve page (`service-approve` widget) showing the service as the server has it, its *destinations* first; approving needs the person's login (an unscoped user access key, or a provider login's ticket: **Page login**) whose user holds `edit_services`, never the page token alone, an OAuth token or a scoped key, and lands only on the service the page showed. Owned by `src/core/serviceApprovals.ts`; reference: `docs/service-approval.md`.
- **Destination** — where a service sends data, as its driver declares it in the config schema (`destinations`: a setting such as the http `url`, or a parameter such as the mail `to` of `send`). Shown first on the approve page and, for the settings a secret is bound to, on the secret form, with the service's pins filled in.
- **Page login** — how a person identifies themself on a page Core serves itself (the OAuth consent screen, the connected-apps page, a service's approve page and its secret form): `identifyPerson` in `src/core/personLogin.ts`, one step shared by all four. Two methods: a full user access key pasted into the page (`pageLogin`, which refuses the sysadmin key, OAuth tokens, scoped keys, and any key where **key login** is off), and a **login ticket** from a **login provider**. A post carrying both is refused. It returns a verified user and nothing more; what the person may then do stays each page's own code. What a page offers is `loginOptions` (`src/core/oidc.ts`).
- **Login provider** — an OpenID Connect provider the operator configures (`YAP_OIDC_PROVIDERS`, `YAP_OIDC_<NAME>_*`); Core is a plain OIDC client of it (code flow, PKCE, its own `state`, nonce, ID token verified against the provider's JWKS). The round trip is one `oidc_transactions` row: created at `/oidc/<name>/start`, claimed once by `/oidc/<name>/callback`, which identifies the person and renders the page the login was for again with a **login ticket** in it. The callback never decides anything: Core has no session to tie a callback to the browser that started it, so the decision is the person's click on that page. A ticket is good once, for ten minutes, for that page and what it is about (the authorize request, or the approval/secret request id). Owned by `src/core/oidc.ts`; reference: `docs/oidc-login.md`.
- **Identity** — a provider's (issuer, subject) linked to a user in `user_identities`: how a returning provider login is recognised, never by email. A first login links one to an **invite** (a user the operator created with an `email` and no identity yet; the email must be one the provider vouches for, per its **provider preset**), or, with `YAP_OIDC_SIGNUP=true` and the address on `YAP_OIDC_ALLOW` (exact, or `@domain`, which under the `google` preset also needs the `hd` claim), creates a user with a personal space and no access key (`createUser` with `initialKey: false`). Either way the user is then **provider login only** (see **Key login**). `users.email` is nullable and unique when set; besides that matching it lets a role grant name its grantee by address (`grant_role` / `POST …/grants` with `email`).
- **Provider preset** — how a **login provider**'s ID token is read (`YAP_OIDC_<NAME>_PRESET`: `generic`, `google`, `entra`): which claim holds the email, whether it counts without `email_verified: true`, which claim is the subject of the **identity**, and whether an `@domain` allowlist entry needs a domain claim (Google's `hd`). Plain data (`OIDC_PRESETS` in `src/config.ts`), with per-claim env overrides; `mapClaims` (`src/core/oidc.ts`) applies it between ID-token verification and matching the person. Default `generic`, or `google` for Google's issuer.
- **Provider grant** — an OAuth grant made on the consent screen after a provider login: `key_id` null, so it belongs to the user and outlives any key; it ends when disconnected, when the sysadmin revokes it (`/v1/users/:id/oauth-grants`), with the user, or at `expires_at`, set at creation from the provider's `GRANT_MAX_DAYS` and never extended by refresh (tokens are clamped to it). A key-backed grant has no `expires_at` and dies with its key. `YAP_OAUTH_MAX_ROLE` caps the role either kind can be granted.
- **Key login** — whether a user access key may be used at all: as a page login, as a `/v1` or `/mcp` credential, and whether a key can be made. Off for the whole instance with `YAP_KEY_LOGIN=false` (needs a login provider), or for one user with **provider login only** (`users.provider_login_only`, set by the sysadmin and by a provider sign-up or invite claim). One refusal decides both, `keyRefusal` in `src/core/keyLogin.ts`, asked by `authenticateKey` and by the key creation guard, with a reason (`key-login-off` / `provider-login-only`, on the wire `details.reason`) each surface words for its reader. Off for the instance, key-backed grants are refused but kept; setting a user's flag deletes theirs. The sysadmin key is never touched. Reference: `docs/key-login.md`.
